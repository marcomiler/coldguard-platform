# Infrastructure as code (Azure)

State of this code: **ready and validated, not provisioned.** Nothing here has run against Azure
until a person approves and applies it. Design and rationale: ADR-012.

| Path | What it is | Lifecycle |
|---|---|---|
| `foundation/` | State storage account, GitHub OIDC identity, empty `rg-coldguard-dev`, budget alerts | Applied once by an Owner, never destroyed |
| `environments/dev/` | Log Analytics, Key Vault, PostgreSQL, Container Apps environment, RabbitMQ, Mailpit and the services | Ephemeral: created and destroyed per usage window |
| `modules/` | `observability`, `keyvault`, `postgres`, `containerapps-env`, `container-app`, `pki` | Reused by `dev` |
| `environments/local/` | Documents that local is Docker Compose | No resources |

## Rules

- No state, plan, `tfvars` with real values or credentials in Git (`.gitignore` covers them).
- The subscription comes from `ARM_SUBSCRIPTION_ID`; no ID is written in the code.
- `plan`, `apply` and `destroy` need explicit human approval and are never run by the assistant or by
  CI on pull requests. CI only runs `fmt -check` and `validate`.
- Passwords, certificates and the JWT key pair are generated by Terraform and stored in Key Vault.
  They also live in the remote state, which is why that storage account is private and out of Git.

## Validate without credentials

```bash
cd infra
terraform fmt -recursive -check
for dir in foundation environments/dev; do
  (cd "$dir" && terraform init -backend=false -input=false && terraform validate)
done
```

## Prerequisites (once, by a person)

1. Register the resource providers in the subscription (free): `Microsoft.App`,
   `Microsoft.DBforPostgreSQL`, `Microsoft.OperationalInsights` and `Microsoft.Web`.
2. `az login` with an Owner of the subscription and `export ARM_SUBSCRIPTION_ID=<id>`.
3. Apply the foundation:

   ```bash
   cd infra/foundation
   cp terraform.tfvars.example terraform.tfvars   # edit owner and budget e-mails
   terraform init && terraform plan -out foundation.tfplan
   # review the plan, then (approval) terraform apply foundation.tfplan
   ```

4. Copy its outputs into the repository variables used by the workflows, and create the protected
   GitHub environment `azure-dev` with a required reviewer.

## Usage window (per demo or evidence run)

```bash
cd infra/environments/dev
cp backend.hcl.example backend.hcl             # state storage account from the foundation output
cp terraform.tfvars.example terraform.tfvars   # owner, ttl and the image tag to deploy
terraform init -backend-config=backend.hcl
terraform plan -out dev.tfplan                 # review
terraform apply dev.tfplan                     # approval required
# ... evidence / demo ...
terraform destroy                              # approval required; do not leave it running
```

The demo users' password is generated; read it from Key Vault (`demo-password`) with the Key Vault
name in the outputs.

## Known unverified points (checked at the first plan/apply)

- Internal gRPC with application-level mTLS over Container Apps TCP ingress, using the app name as
  host (the certificate SANs match the names).
- One secret volume mounted at several folders of the same container.
- PostgreSQL Flexible Server availability of the Burstable SKU in the chosen region.
- The Docker Hub RabbitMQ image can be rate limited when pulled from Azure.
